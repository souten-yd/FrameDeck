# 連続ページ送りの待ち時間・負荷の抑制

## 調査結果

実機の停止時ログは未取得。コード上で以下の負荷増幅経路を確認した。

1. ページ送りAPIを制限なく同時送信でき、サーバーのエンジンロック前で要求が滞留する。
2. 毎ページで一覧全体を再描画するため、大量の漫画・フォルダがあるとブラウザのメインスレッドを占有する。
3. サイズ確認が `exif_transpose` による全画像のデコードとコピーを伴う。ページ送りの見開き判定と先読みで繰り返される。
4. サーバーの先読みは同一ページの重複だけを排除し、移動済みのページへの待ちジョブを保持していた。
5. メモリLRUに容量上限超過の画像を入れると、既存の有用なキャッシュを全て追い出し、最終的に大きな画像自身も捨てる。

## 対策

- ページ送りAPIはブラウザごとに1件まで。同時入力は蓄積しない。失敗時も制限を解除し、別セッションを開いた後の古い応答を適用しない。
- 巻・選択が変わった時だけ一覧を再描画する。
- 寸法はヘッダーとEXIF Orientationから判定し、画素のデコードを不要にする。
- サーバーの先読みは実行中を含め最大16件。現在の先読み範囲外と解放済みソースのジョブは処理せず終了する。アーカイブが読取中なら先読みを見送り、表示用読み取りの後ろに並ばない。
- 上限超過の画像はメモリキャッシュに入れず、既存キャッシュを保持する。通常の読み込みではソースロック内でキャッシュへ格納し、格納前に別要求が重複読取する隙間をなくす。

## サーバーキャッシュの評価

QNAP既定はメモリ64MB、変換画像ディスク32MB。原寸配信では主にメモリキャッシュを使うため、変換画像キャッシュの削除は通常の原寸画像配信には直接関与しない。ディスク整理は10分間隔のバックグラウンド処理で多重実行防止済み。キャッシュ容量を単純に増やす変更は行っていない。

回帰テストは遅延応答中の100操作、API失敗からの復帰、旧セッション応答破棄、100回の先読み範囲変更、画像デコード回数、容量超過挿入を検証する。実機で継続する場合は画像形式（ZIP/RAR/7z）、停止中のHTTP応答・NAS負荷を追加調査する。
