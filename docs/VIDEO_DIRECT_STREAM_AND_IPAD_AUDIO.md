# 原版動画配信と iPad 音声の修正（v2.4.19）

## コードから特定した問題

1. Web UI の動画音量スライダーは `value="0"` で初期化され、再生開始時に
   `video.volume = 0` を実行していた。通常のブラウザでは無音になる。
   iPadOS Safari の `volume` は JavaScript から設定できないため、
   iPad ではデバイスの音量ボタンで調節する。
2. Linux の通常プロファイルは明示的な「原寸」指定時に、
   直接再生可能な元ファイルでも fMP4 Remux を強制していた。
   原版は元ファイルのHTTP Range配信を基本にするべき。
3. iPad Safari は `canPlayType` で音声対応を示しても、
   一部の非AAC音声で無音になる可能性がある。
4. QNAP Range配信の先読みキューが満杯のとき、正常終了の通知
   `None` が失われて送信が停止し得る経路があった。

## 変更と配信判断

- 初期音量を100%（ミュートなし）に変更。iPhone/iPadではアプリ内の音量スライダーを無効化し、機器の音量操作を案内する。ミュートボタンは残す。
- Linux と QNAP 両方で、ブラウザが音声・映像・コンテナを扱えるときは元ファイルの `/api/videos/{id}/stream` を使用し、FFmpegを起動しない。
- iOS/iPadOSでは AAC/MP3以外の音声トラックを保守的に非互換扱いとする。映像コーデックが再生可能なら映像を `-c:v copy` し、音声だけ `-c:a aac` のHLS `original-aac` にする。
- 映像自体が再生不可能なときだけ従来の変換上限を適用。QNAPのエンコード同時数、HLS変換制限、セグメントキャッシュ制限を維持する。
- 明示した「remux」選択は引き続き利用できる。元ファイルのコンテナや音声コーデックに互換性がない場合も必要なRemux/音声変換を維持する。
- 非同期のフォルダ取得はモードと要求世代が一致する場合だけ画面に反映する。
- 先読みキューはQNAPで4MiBまでとし、通常終了時の終端通知を必ず届ける。

## 注意点と検証範囲

- 「原版」はその動画のブラウザ対応を意味しない。VLCはブラウザより幅広いデコーダを持つため、対応しない動画は変換が必要。
- `original-aac` は映像そのものを再圧縮しないが、音声変換とHLSセグメント生成によるCPU・ディスクI/Oはある。キーフレーム間隔が長いファイルは最初のセグメント生成に時間がかかる。
- 再生開始がSafariの自動再生制限で拒否された場合、ユーザーに再生ボタンを押すよう通知する。
- NASとiPadの実機テスト、VLCとの転送速度比較は別途必要。
  実機では動画コンテナ/映像・音声コーデック/映像解像度/実際の再生バッジと、
  サーバ側の `配信元の読み出しが遅延` 警告を記録する。
- テストはモード切替の競合、音声コーデック判定、HLSのFFmpegオプションと
  Range EOF通知、および既存API/JSの後方互換を対象とする。
